# 面试讲述指南

## 1. 先立边界

这个仓库是 **自己搭的可复现 Demo**，不是某公司真实上线系统。面试时建议这样开场：

> “我做了一个环保设备租赁场景的 AI 产品作品集 Demo，用合成数据复现了客服 Agent、内容 Workflow 和投标摘要。它不是公司项目，但流程、评测和代码都是我按真实产品标准做的。”

这句话有三个作用：

1. 建立可信度，不夸大。
2. 把话题引到“你怎么做”，而不是“你做了多大”。
3. 避免面试官追问真实公司数据时无法回答。

## 2. 3 分钟 Demo 脚本

### 0:00—0:30 背景

> “环保设备租赁的客服重复问题多，报价和订单又要精确。我想验证：哪些问题可以自动答，哪些必须转人工；以及怎么用评测证明它可靠。”

### 0:30—1:20 客服 Agent

打开 Web Demo 的“客服 Agent”：

1. 输入“租赁 2 台移动式污水处理设备 10 天多少钱？”
2. 指出输出：设备、数量、天数、租金、优惠、安装、运输、税费、押金、合计。
3. 说明：报价不是模型算的，是 `get_quote` 工具算的。
4. 输入“订单 EQ2026003 什么进度？”
5. 说明：订单查询走 `get_order_status`，返回节点、ETA、负责人。
6. 输入“设备故障三天没人处理，我要投诉，转人工。”
7. 说明：投诉直接建工单，Agent 不做承诺。

### 1:20—2:00 内容 Workflow

1. 输入“污水设备租赁的 5 个成本坑”。
2. 展示 3 个标题、脚本、配图提示词、合规分、审核状态。
3. 说明：合规检查是规则，不是模型“自觉”；高风险内容状态会变成 `needs_revision`。
4. 切到数据问答：“哪个渠道线索最多？”
5. 说明：90 条合成数据，输出渠道、CPL、转化率；结论只用于演示。

### 2:00—2:40 投标与流程

1. 输入“园区污水处理项目的投标截止时间和预算是什么？”
2. 展示引用：文件名 + 原文。
3. 说明：招标文件先做规则抽取，保留原文，降低幻觉。
4. 打开 `reports/process_opportunities.md`：19 个节点、Top 6、优先级公式。
5. 说明：高风险节点（投诉、合同用印）建议“AI 辅助 + 人工复核”。

### 2:40—3:00 评测与反思

> “我建了 60 条评测，当前 Hit@1 92%，意图和工具 100%，困难子集只有 60%。失败主要是‘开票/发票’‘被偷/丢失’这类同义词。下一步会做 query expansion 和真实日志回流。这个项目最大的收获是：AI 产品的难点不是接模型，而是定义边界、做评测、设计兜底。”

## 3. STAR 故事

### 故事 A：客服 Agent 的边界

- **Situation**：客服重复问题多，报价/订单必须精确，投诉不能乱承诺。
- **Task**：设计一个能自动回答常见问题、但不越权的 Agent。
- **Action**：
  - 把问题分成 FAQ / 报价 / 订单 / 转人工 / 超范围。
  - FAQ 用 BM25 + 引用；报价/订单用工具；投诉直接建工单。
  - 设定置信度阈值，低分转人工。
  - 建 60 条评测，保留失败案例。
- **Result**：
  - 合成评测 Hit@1 92%，意图/工具 100%。
  - 困难子集 60%，明确下一步 query expansion。
- **Reflection**：产品经理的价值不是“让 AI 更聪明”，而是“让 AI 在该停的时候停”。

### 故事 B：内容 Workflow 的合规检查

- **Situation**：内容生成容易写出“保证”“100%”“行业第一”等违规词。
- **Task**：让内容生产更快，同时不把风险带给品牌。
- **Action**：
  - 把流程拆成 Brief、标题、脚本、配图、合规、审核。
  - 合规检查用确定性规则，覆盖绝对化用语、数字承诺、语气。
  - 高风险内容状态改为 `needs_revision`，必须人工改。
- **Result**：单篇内容可以结构化产出；合规问题在生成阶段被拦截。
- **Reflection**：生成式 AI 的产品设计，重点在“生成后的检查”和“人工节点”。

### 故事 C：投标文件的结构化抽取

- **Situation**：招标文件长，关键日期、预算、资质、评分、废标条款分散。
- **Task**：快速输出可复核的投标检查清单。
- **Action**：
  - 按标题/句子切分，正则抽日期、金额、项目编号。
  - 关键词抽资格、技术、商务、评分、风险条款。
  - 保留原文，不做模型改写。
  - 增加跨文件 BM25 检索。
- **Result**：3 份合成招标文件可输出结构化摘要和带引用问答。
- **Reflection**：高风险文档场景，宁可“少总结”，也要“可追溯”。

### 故事 D：流程机会矩阵

- **Situation**：流程很多，不知道先自动化哪个。
- **Task**：用统一口径排优先级。
- **Action**：
  - 拆 4 条流程、19 个节点。
  - 记录平均耗时、月发生量、自动化潜力、风险、数据就绪度。
  - 用“月工时 × 潜力 × 数据就绪度 / 风险”排序。
  - 高风险节点先辅助、不自动。
- **Result**：Top 6 机会点，先做日报取数和日常咨询。
- **Reflection**：AI 产品不是“能自动就自动”，而是“先做值得做、做得到的”。

### 故事 E：为什么默认不接大模型

- **Situation**：作品集需要可复现、零成本、CI 稳定。
- **Task**：既要展示 AI 能力，又不能依赖 API Key。
- **Action**：
  - FAQ 用检索 + 模板化 grounded composer。
  - 报价/订单用确定性工具。
  - 内容用模板 Writer + 合规规则。
  - 预留 LLM Prompt 和接入点。
- **Result**：23 个测试稳定通过，任何人都能一键跑。
- **Reflection**：先用最轻的方案验证产品逻辑，再决定是否值得接模型。

## 4. 常见追问

### Q：这和直接用 Dify 搭有什么区别？

> “Dify 能快速搭出 RAG/Agent，但作品集里我更想展示三件事：第一，我知道什么时候不该用模型；第二，我有评测和失败分析；第三，我能把工具、数据、文档和代码组织成可复现的工程。Dify 是实现手段，不是产品能力本身。”

### Q：你的准确率 100% 是真的吗？

> “不是生产准确率。意图和工具在 60 条合成用例上是 100%，检索 Hit@1 是 92%，困难子集只有 60%。我在报告里保留了失败案例，因为真实用户的口语化问法会更多。”

### Q：你做过真实用户访谈吗？

> “仓库里的访谈是合成材料，用来练习访谈到洞察的方法。如果面试需要，我可以讲真实项目里我做过的调研，但不会把合成访谈说成真实调研。”

### Q：如果给你真实数据，你第一步做什么？

> “先做数据审计和 50—100 条真实问题采样，确认高频意图、知识库覆盖、错误成本和人工接管点；然后用同一套评测跑基线，再决定是优化检索、补知识库还是换模型。”

### Q：你怎么和工程师协作？

> “我会把需求写成输入输出、失败码、置信度阈值、人工接管、评测集和回归门槛。比如报价工具，我会定义参数校验、金额口径、舍入规则、异常提示，而不是只说‘做一个报价功能’。”

## 5. 简历 bullet 建议

不要写“搭建了企业级 Agent”。建议写：

> - 独立复现环保设备租赁客服 Agent：210 条知识库、4 个工具、60 条评测；合成评测 Hit@1 92%，意图/工具选择 100%，困难子集 60%。
> - 设计内容生产 Workflow：Brief → 脚本 → 配图提示词 → 合规检查 → 审核；用 90 条合成数据做渠道/选题/CPL 分析。
> - 复现投标摘要与流程机会矩阵：3 份招标文件结构化抽取，19 个流程节点排序，输出 Top 6 自动化机会。

如果简历里要写“某公司实习”，必须用真实公司、真实项目、真实数据；不要用本仓库的合成数据冒充。

## 6. 不要做的事

- 不要把 Demo 说成“公司上线系统”。
- 不要把合成指标说成“生产指标”。
- 不要把 100% 说成“准确率”。
- 不要把别人的框架说成自己从零实现。
- 不要只讲工具，不讲问题、边界和评测。
- 不要背稿，要能现场打开代码和报告。

## 7. 反问面试官

1. 公司目前 AI 化转型最想解决的三个业务问题是什么？
2. 哪些环节已经有人在做？是自研、Dify/Coze 还是外包？
3. AI 项目的验收标准是什么？谁对最终效果负责？
4. 数据在哪些系统里？知识库由谁维护？
5. 这个实习生岗位 6 个月最希望交付什么？
6. 团队怎么看待“AI 出错”与人工接管？
